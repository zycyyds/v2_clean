## 六、读数须知（四条不看会读错）

### ① 同种子重跑**不保证**复现 —— 小于 ~0.011 的差值不可判定

`model_config.yaml` 固定了 `temperature: 0.0` / `seed: 666`，
但 **icu5000 1.6pct 用同一份 prompt（sha256 逐位相同）跑三次，第 4 轮分数是
0.892868 / 0.903023 ⇒ 差 0.010155**。
根因不是采样噪声，是**多轮 val 反馈闭环把扰动放大了**（每轮把得分和反馈喂回 agent）。

⇒ **icu5000 1.6pct 我们比 codex 高 0.001139 = 噪声内，正确说法是「打平」。**
⇒ I48 1.6pct cc 比我们高 0.006166 **也小于这个量级**。
真正可判定的差值：N18 1.6pct（+0.021205）、icu5000 4.7pct（−0.017265 / −0.033373）。
（test 阶段是纯重放、无 LLM，那一层是可复现的 —— 每条记录 `reproducible_score == best_score`。）

### ② cc 的错误级指标被 cc 自己制造的损失污染

N18 4.7pct cc 的 `b_missing` = 2,684,119、I48 1.6pct = 1,140,639，
**大部分不是「没检出脏数据」，是 cc 的 pipeline 自己把 gold 里真实存在的行删了**
（N18：删 `itemid=='999001'` −1,184,531 行 + 8 列去重 −643,177 行；
I48：`itemid` 前缀没剥掉 ⇒ `matched_key_rows = 0/374,003`）。
⇒ **cc 的 Det/Rep 与我们的不可直接比。**

### ③ `hospital_expire_flag` 是一条标签泄漏通道

我们 agent 的 `pipeline.py:282-283` 用 `deathtime` / `discharge_location=='DIED'`
把 `hospital_expire_flag` **完全修对**（train 上 23/23），再由 `:344` 复制进 `cohort.csv`
⇒ **交付的结果包自带一列近乎完美的院内死亡标签**。
下游做死亡预测时**必须 drop 掉这一列**，且标签必须从 gold 的 `dod` + 住院窗口现算。

### ④ K29 1800（低密度档）的 Det/Rep 看着很差，**是口径假象，不是能力差**

这一档 test 只有 **1,800 条错误**（`cell_update 1,673` + `duplicate 73` + `insert 54`）：

| | 值 | 说明 |
|---|---:|---|
| Det **R** | **0.997778** | **只漏 4 个 / 1,800 ⇒ 几乎全检出** ✅ |
| Det **P** | 0.145073 | FP = **10,584**，**其中 10,514 是假象**（见下）|
| Rep R / P | 0.577222 / 0.083926 | 1,039 格修对、757 格改错（**有一部分也是假象**）|
| composite | **0.996510** | 真实不一致 cell 只有 **659** 个（见下）|

🔴 **假象机制**：错误级指标（`error_metrics/`）给每张被注入表用的 row-identity key
比 harness manifest **窄**（chartevents **5 列**，不含 `valuenum`/`valueuom`；
inputevents / outputevents 同理），查表取「该 key 下**第一个命中**」。
而这些表在窄 key 上**大量重复**（K29 1800 的 gold chartevents：293,363 个重复 key 组、
139 万行落在里面）⇒ agent 和 gold 在同一组里可能被取到**不同的物理行**
⇒ **把「取错行」记成了「误改干净 cell」**。

**实测**（同一个查表动作，只换 key 宽度）：

| 表 | 窄 key 撞错 | 宽 key 撞错 |
|---|---:|---:|
| `icu/chartevents.csv` | **10,496** | **0** |
| `icu/inputevents.csv` | **32,447** | **0** |
| `icu/outputevents.csv` | **101** | **0** |

⇒ **`fp_det` 里 chartevents 的 10,514 就是这么来的**（10,496 个撞错的 key 各贡献 1~2 个 cell）。
`admissions` / `demographics` 的 key 唯一（0 重复组）⇒ 它们的数字是真的。

✅ **harness 自己口径的真相**（宽 key + 数值归一化，逐格比）：

| | 数字 |
|---|---:|
| 对齐上的行 | 12,218,143 |
| 完全一致的行 | 12,217,485 |
| **不一致的 cell（12 个文件合计）** | **659**（demographics 545 + admissions 111 + inputevents 3）|
| **真实误伤干净 cell** | **70**（全在 admissions）|
| key 对不上而整行丢失 | 21,292 行 |

⇒ **composite 失分的大头不是「多改」**，而是 **key 里含被修复的列** ——
agent 把 `valuenum`/`valueuom`/`value`/`amount` 修对了 ⇒ **key 变了 ⇒ 整行对不上 ⇒ 该行 0 分**。
⇒ **K29 1800 的 Det/Rep 不能跟别的档横向比**；
**横向可比的是 composite 0.996510 和 Det R 0.997778**。
⇒ 行级两类错误倒是**清得干干净净**：`duplicate_row` 73 → `dup_removed` 73 / `dup_kept` 0；
`label_leakage_feature` 54 → `leak_removed` 54 / `leak_kept` 0。
