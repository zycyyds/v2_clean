# 数据清洗结果包评测规范

> **给任何执行者（人 / AI）**：本文档定义「拿到一个 data-cleaning agent 产出的结果包，
> 怎么评它」。不需要理解项目历史，照着做即可。
>
> 目标：让多个互不相同的 AI（codex / 豆包 / workbuddy / …）对**同一批结果包**
> 独立打分，产出可交叉验证的结论。

---

## 0. 你要做的事（一句话）

**给定一个结果包目录 + 一个 gold 目录，算出两个数：**
1. **Raha composite**（总分，0-1，越高越好）
2. **错误级指标**（Det F1 / Rep F1 + 分桶明细，可选但强烈建议）

然后把结果写进约定的 JSON，并**对照 §7 的历史基线自检**。

---

## 1. 输入是什么

### 1.1 结果包（被评对象）

一个目录，里面有 **13 个 csv**（目录结构必须保持一致）：

```
<result_root>/
├── admissions.csv              cohort.csv            demographics.csv
├── diagnoses.csv               procedures.csv        medications.csv
├── labs.csv
├── icu/icustays.csv            icu/chartevents.csv
├── icu/inputevents.csv         icu/outputevents.csv
└── multimodal/ecg_manifest.csv
    multimodal/ecg_measurements.csv
```

**检查点**：13 个文件都在吗？`submission.json` 有吗（`result_root` 是相对路径）？
多余的文件（如 `summary.json`）不影响评分，评分器会忽略。

### 1.2 gold（标准答案）

对应数据集的 `test/reference/` 目录，同样是 13 个 csv。
**gold 从哪来**：跟结果包用同一个数据集的 `test/reference`。

> ⚠️ **gold 只能给评测方，不能给被评的 agent。** 如果你就是被评 agent 的开发者，
> 千万别让 agent 读到 gold 或 modification_log。

### 1.3 完整数据集（只有算错误级指标才需要）

```
<dataset_dir>/
├── test/raw/                  ← 注入错误的原始数据
├── test/reference/            ← gold
├── test/modification_log.csv  ← ⚠️ 答案！只有评测脚本读，人和 agent 都不能看
└── v2_rawerror_*.json         ← 注入统计报告
```

### 2.3 错误级指标（强烈建议）

**为什么建议做**：composite 是一个数，看不出「哪类错没修」。错误级指标给的是
「修了多少 / 改错多少 / 丢了多少行 / 误改多少」。

```bash
# 第一步：建缓存（读结果包 + gold + 注入日志）
python3 error_metrics/build_eval_cache.py \
  --result-dir <结果包目录> \
  --ref-dir   <dataset_dir>/test/reference \
  --ds-key    <一个命名空间，随便起，如 my_run>

# 第二步：逐 cell 分类记账
python3 error_metrics/compute_error_metrics.py \
  --dataset-dir <dataset_dir> \
  --ds-key      <跟上面同一个> \
  --split       test \
  --out         <输出.json>
```

**耗时**：4.7pct 数据集约 1.5 小时（扫 3,200 万条注入日志 + 逐 cell 比对）。
1.6pct 约 28 分钟。**纯 CPU，可以放后台跑。**

**输出**：

```jsonc
{
  "recover_clean_key": true,          // ← 口径标记，务必确认
  "detection": { "P": ..., "R": ..., "F1": ... },   // 检测：改对了多少
  "repair":    { "P": ..., "R": ..., "F1": ... },   // 修复：改对了多少且完全正确
  "buckets": {
    "b_clean":     6780285,   // 干净 cell 改对了
    "b_dirty":      54282,   // 脏 cell 没动（漏检）
    "b_wrong":    1425083,   // 脏 cell 改了但改错了
    "b_missing":     8972,   // 整行丢了
    "fp_det":          48,   // 干净 cell 被误改
    "dup_removed": 1313409, "dup_kept": 223,
    "leak_removed":  295259, "leak_kept": 0,
    "crow_recovered": 3912163,   // key 被破坏但救回的行
    "natural_noise": 9974997      // raw↔gold 天然落差（已从 P/R 分母剔除）
  }
}
```

## 3. composite 是怎么算的（用于判断结果是否合理）

**13 个文件等权**（每文件 1/13），**文件内**四项加权：

```
file_score = 0.1 × schema_f1
           + 0.2 × key_structure_f1
           + 0.4 × row_aligned_cell_f1
           + 0.3 × exact_row_f1

composite_score = mean(13 个 file_score)
```

四项的含义：

| 指标 | 含义 | 看什么 |
|---|---|---|
| `schema_f1` | 列名/列数是否与 gold 一致 | 结构完全对不上时会掉 |
| `key_structure_f1` | 主键结构 | 主键列定义错会掉 |
| `row_aligned_cell_f1` | **按主键对齐后逐 cell 的 F1** | 权重最大，主战场 |
| `exact_row_f1` | 完全一致的行占比 | 整行对不对 |

**主键（key_columns）由 manifest 定义**，ic u5000 的是：

| 文件 | 主键 |
|---|---|
| admissions.csv | hadm_id |
| cohort.csv | subject_id + hadm_id |
| demographics.csv | subject_id |
| diagnoses.csv | subject_id + hadm_id + seq_num + icd_code + icd_version |
| procedures.csv | 同 diagnoses |
| medications.csv | subject_id + hadm_id + starttime + stoptime + drug + dose_val_rx + dose_unit_rx + route |
| labs.csv | subject_id + hadm_id + itemid + charttime + valuenum + valueuom |
| icu/icustays.csv | stay_id |
| icu/chartevents.csv | subject_id + hadm_id + stay_id + charttime + itemid + valuenum + valueuom |
| icu/inputevents.csv | subject_id + hadm_id + stay_id + starttime + itemid + amount |
| icu/outputevents.csv | subject_id + hadm_id + stay_id + charttime + itemid + value |
| multimodal/ecg_manifest.csv | study_id |
| multimodal/ecg_measurements.csv | study_id |

**对齐方式**：按主键做 key join，行按主键排序后逐 cell 比。
**多出/缺失的行**分别记 `extra_result_rows` / `missing_reference_rows`，
并且会让 `exact_row_f1` 掉。**丢行比改错值更伤**（行丢了，key 对不上，
整行所有 cell 都算错）。

## 4. ⚠️ 口径规矩（最容易出错的地方）

错误级指标有**三套口径**，绝对不能混用：

| 口径 | 怎么产生 | 行为 |
|---|---|---|
| **v29（当前，默认）** | 默认 | ① key 列被注入破坏时，先把该行 key 还原成干净值再定位；② **只评 gold 里也存在的行** |
| v28 | 加 `--keep-rows-not-in-gold` | 不排除「gold 里也不存在」的行 |
| 旧口径 | 加 `--no-recover-clean-key` | ① 不还原 key；② 不排除 gold 外行 |

### 为什么必须有第 ② 条（N18 上踩过的坑）

N18 的 raw 是 MIMIC 原始表（`icu/chartevents.csv` 918 万行），gold 是聚合后的 659 万行 ——
**raw 比 gold 多出来的 259 万行，agent 正确删掉了**。但这些行里也有注入错误，
v28 会把它们记成 `b_missing`（漏检）。

实测（N18 1.6pct，我们的 agent）：

| | b_missing | Det F1 | Rep F1 |
|---|---:|---:|---:|
| v28（不排除 gold 外行） | 3,490,901 | 0.699140 | 0.555167 |
| **v29（排除 gold 外行）** | **3,247** | **0.997427** | **0.792025** |

被排除的 3,487,654 个格子全部落在 2,745,855 个「gold 里本来就没有」的行上 ——
这些根本不是 agent 能修的目标。**v28 的 0.699 是纯口径假象，不是 agent 水平。**

### 另一套口径的差距（key 还原，icu5000 1.6pct）

| | b_missing | Det F1 | Rep F1 |
|---|---:|---:|---:|
| v29 | 8,972 | 0.996719 | 0.851930 |
| 旧口径（不还原 key） | **2,826,200** | 0.829509 | 0.733281 |

**规矩**：
1. **对外只报 v29**
2. 比较两个结果前，**先看两边 json 里的 `recover_clean_key` 和 `exclude_rows_not_in_gold` 字段是否相同**
3. 旧口径只在跟更早的历史 run 横比时用

**composite 没有这个问题** —— 它跟口径无关（composite 由 gold 算出，不看注入日志）。

> **判断你的数据集会不会中招**：看 `test/raw/icu/chartevents.csv` 的行数 vs
> `test/reference/icu/chartevents.csv` 的行数。raw 明显更多 → 一定会中招，
> 必须用 v29。icu5000 的 1.6pct 是「事后 diff raw↔gold」造的，注入错误天然只落在
> gold 存在的行上，所以 v28/v29 差别很小；N18 / 4.7pct 这类「注入引擎」造的就会中招。

### ⚠️ 另一条规矩：同种子重跑**不保证**复现 ⇒ 小于 ~0.011 的差值不可判定

我们的 agent 配了 `temperature: 0.0` / `seed: 666`，
但 **icu5000 1.6pct 用同一份 prompt（sha256 逐位相同）跑三次，第 4 轮的分数是
0.892868 / 0.903023 ⇒ 差 0.010155**。

根因不是采样噪声，是**多轮 val 反馈闭环把扰动放大了**：
每轮 harness 把上一轮的得分 + 公开反馈喂回 agent ⇒ 分数不同 ⇒ 反馈不同 ⇒ 下一轮行为不同
⇒ 两条轨迹越走越远。
（**test 阶段是纯重放、无 LLM，那一层是可复现的** —— 每条记录 `reproducible_score == best_score`。）

⇒ **横比时**：composite 差值 **< 0.011 ⇒ 判不出胜负**，别写成「A 比 B 好」。
历史上踩过的坑：icu5000 1.6pct 我们比 codex 高 0.001139 —— 那在噪声里，正确说法是**打平**。
⇒ 差值 > 0.011 的才算可判定：N18 1.6pct（+0.021205）、icu5000 4.7pct（−0.017265 / −0.033373）。

### ⚠️ 第三条规矩：`hospital_expire_flag` 是标签泄漏通道

注入的确实是错误（任务书把 `hospital_expire_flag` 整列取反），
**任何认真修的 agent 都会把它完全修对**（我们 agent 用 `deathtime` / `discharge_location=='DIED'`
重算，train 上 23/23 精确命中），而且会把它复制进 `cohort.csv`。

⇒ **交付的结果包自带一列近乎完美的院内死亡标签。**
⇒ **下游做死亡预测时必须 drop 掉这一列**，
且标签必须从 gold 的 `dod` + 住院窗口现算（`dod ∈ [admittime, dischtime]`），
**绝不能拿 agent 输出的 `hospital_expire_flag` 当标签**。

## 5. 怎么读结果（诊断表）

拿到分数后，按这个顺序看：

| 现象 | 大概率原因 | 怎么进一步确认 |
|---|---|---|
| composite < 0.5 | 结果包结构就不对（文件缺失/放错层/多套了一层目录） | 看 `file_reports[].status`，有没有 `missing` |
| 某些文件 `exact_row_f1` 接近 0 但 `row_aligned_cell_f1` 还行 | 整行对不上 —— **丢了行或多了行** | 看 `missing_reference_rows` / `extra_result_rows` |
| `row_aligned_cell_f1` 明显低但 key 正常 | cell 值修错了 | 错误级指标的 `b_wrong` |
| `b_missing` 特别大 | 整行被丢了 | 检查 agent 的过滤规则是不是太激进 |
| `b_wrong` 特别大 | 改了一堆但改错 | agent 是不是在"猜"值 |
| `fp_det` 不为 0 | 误改干净 cell | agent 的检测规则太宽松 |
| `leak_kept` 不为 0 | 标签泄露行没清掉 | 泄露检测规则缺失 |
| 某文件 composite 特别低但它错误量很小 | **大概率是丢行** | 看 `missing_reference_rows` |

## 6. 交付格式

每个执行者输出**一个 JSON**，结构固定，便于交叉比对：

```jsonc
{
  "evaluator": "<你的名字/模型标识>",
  "dataset": "icu5000_less_1.6pct",
  "result_package": "<被评的结果包路径>",
  "raha": {
    "composite_score": 0.897831,
    "schema_f1": 1.0,
    "key_structure_f1": 0.945922,
    "row_aligned_cell_f1": 0.926070,
    "exact_row_f1": 0.793424,
    "per_file": { "admissions.csv": 0.671934, ... }
  },
  "error_metrics": {                      // 算了就填，没算就 null
    "recover_clean_key": true,
    "detection_f1": 0.996719,
    "repair_f1": 0.851930,
    "buckets": { ... }
  },
  "sanity_check": {
    "within_expected_range": true,        // 对照 §7 判断
    "note": "..."
  }
}
```

**同时附一份人话摘要**（3-5 句）：总分多少、跟基线比如何、最大的短板是哪个文件/哪类错。

## 8. 常见故障

| 症状 | 原因 | 处理 |
|---|---|---|
| `ModuleNotFoundError: workflow` | 没在正确的目录下跑 | `cd` 到 score_only 包根目录，或 `export PYTHONPATH=<score_only 包根>` |
| `reference directory contains no comparable structured files` | gold 路径错 | 检查 gold 目录里有没有 13 个 csv |
| `missing key configuration: <file>` | manifest 与 gold 不匹配 | 换对 manifest |
| `ambiguous_file` | 结果包里有重名文件 | 检查 result_root 下的文件树 |
| composite = 0.49 左右 | 结果包多套了一层目录（`result/result/`） | 13 个 csv 要**直接**在 result_root 下 |
| 某些文件 status 是 `missing` | 结果包缺文件 | 补齐或确认该文件本就不产出 |
| 错误级指标跑很久 | 正常（1.5h / 4.7pct） | 放后台 |

## 9. 绝对不要做的事

| ❌ | 原因 |
|---|---|
| 为了让分数好看而改评分代码 | 分数会跟历史不可比，整个评测失去意义 |
| 混用新旧口径报数字 | 见 §4 |
| 只报 composite 不说口径 | 别人没法判断可比性 |
| 改了结果包再来打分 | 那不叫评测 |
| 把 gold 或 modification_log 泄漏给被评 agent | 那是答案 |
| 硬编码 subject_id / hadm_id / stay_id / 行号去「修」结果包 | 那是作弊，不是清洗 |
