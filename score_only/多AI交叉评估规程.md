# 多 AI 交叉评估规程

> 目的：让 codex / 豆包 / workbuddy / Claude Code 等**多个互不相同的 AI**，
> 对**同一批结果包**独立打分，产出可交叉验证的结论。
>
> 为什么要交叉：**单一评分者的判断可能受自己实现细节影响**。
> 多个 AI 用同一套规范独立跑，分数一致 → 结论可信；分数不一致 → 说明
> 规范有歧义或有实现分歧，需要人来看。

---

## 0. 角色分工

| 角色 | 谁做 | 产出 |
|---|---|---|
| **被评方** | 跑了清洗的 agent | 结果包（13 个 csv） |
| **评分方** | 任意一个 AI | 一份评分 JSON + 人话摘要 |
| **协调方** | 你（人） | 汇总、发现分歧、裁决 |

**关键**：多个评分方**互不可见**对方的分数和代码 —— 否则会互相污染，
失去交叉验证的意义。

---

## 1. 怎么组织一次交叉评估

```
第 1 轮：所有评分方拿到【同一个包 A】的规范，独立打分 → 汇总
         ↓ 如果分数一致（±0.002 内），说明规范清晰，进入第 2 轮
         ↓ 如果不一致，把差异归因（§4 排查），修规范再来一轮
第 2 轮：所有评分方拿到【同一个包 B】（不同 agent 的产出）→ 汇总
         → 分数差异 = agent 之间的真实能力差异
```

**先用一个已知答案的包校准**（§5 有历史基线），确认每个评分方的实现没问题，
再评真正要比的包。否则分不清是「agent 差」还是「评分方实现有 bug」。

## 2. 交给每个评分方的东西

**只给三样**：

1. `score_only/` 整个目录（含 `评测规范.md` + 脚本）
2. 被评的结果包目录
3. 对应的 gold 目录（`test/reference`）

**明确告诉它**：
- 照 `评测规范.md` 执行，不要改评分代码
- 输出格式见 `评测规范.md` §6
- 遇到 `评测规范.md` §8 的故障先查表
- 算完把 JSON + 3-5 句摘要发回来

**给它的一句指令模板**（`评测规范.md` §10 也有）：

> 你要评测一个 data-cleaning agent 的产出。请严格按 `score_only/评测规范.md` 执行：
> 1. 跑 §2.2 拿 Raha composite，跑 §2.3 拿错误级指标
> 2. 按 §6 的 JSON 格式输出，附 3-5 句人话摘要
> 3. 按 §7 对照基线自检，异常按 §5 诊断表查
> 4. **不要修改评分代码**
> 5. 遇到 §8 故障先查表再动手

## 3. 每个评分方要交的东西

一份 JSON（格式见 `评测规范.md` §6）+ 3-5 句人话摘要。

**必须包含的**：

| 字段 | 为什么 |
|---|---|
| `evaluator` | 谁评的 |
| `dataset` | 哪个数据集、哪个错误率档 |
| `result_package` | 被评的包路径 |
| `raha.composite_score` | 总分 |
| `raha.per_file` | 逐文件 —— **交叉验证时这是最有用的字段** |
| `error_metrics.recover_clean_key` | 口径标记 ① |
| `error_metrics.exclude_rows_not_in_gold` | 口径标记 ②（v29 新增） |
| `error_metrics.buckets` | 分桶明细 |
| `sanity_check` | 它自己觉得正不正常 |

## 4. 汇总后怎么判分歧

拿到 N 个评分方的结果，先按 §4.1 对齐口径，再看 §4.2 的分歧归因。

### 4.1 先查口径

```bash
# 所有评分方的两个口径标记都必须一致
jq -r '.error_metrics.recover_clean_key' 评分方*.json | sort -u
jq -r '.error_metrics.exclude_rows_not_in_gold' 评分方*.json | sort -u
# 每个都只能输出一个值
```

不一致 → **不是 agent 的问题，是口径混了**，全部重算。

> 口径 ②（`exclude_rows_not_in_gold`）是 v29 新加的：不排除的话，
> **agent 正确删掉的、gold 里本来就没有的行**里的注入错误会被记成漏检。
> N18 上这一项让 Det F1 从 0.699 变成 0.997 —— 跨评分方比较前一定要对齐它。
> 详见 `评测规范.md` §4。

### 4.2 再看分数

| 现象 | 含义 | 处理 |
|---|---|---|
| 全部一致（±0.002） | 规范清晰，实现一致 | ✅ 可以信任 |
| composite 一致但 per_file 不一致 | 分数凑巧撞上，但实现细节不同 | ⚠️ 看是哪个文件不一致，多半是某个文件被跳过/权重算错 |
| composite 差 > 0.005 | **规范有歧义** | 逐文件 diff，找第一个分歧点 |
| 某方分数明显偏低 | 该方实现有问题 | 走 §4.3 排查 |

### 4.3 常见实现分歧

| 症状 | 原因 |
|---|---|
| 某些文件 status=`missing` | 结果包路径没找对（多套了一层目录） |
| composite ≈ 0.49 | 结果包多套了一层 `result/result/` |
| `row_aligned_cell_f1` 比别人低很多 | 主键定义取错（manifest 没传对） |
| `exact_row_f1` = 0 但别人正常 | 结果包行数对但排序/换行符不同 |
| 报错 `ambiguous_file` | 结果包里有重名文件 |
| 某个文件被跳过 | 那个文件的 manifest 缺失或 key 列不匹配 |

**分工原则**：先查每个分方的 stderr/日志，再比对 per_file。

## 7. 判读结果时的注意事项

1. **composite 差 0.001-0.002 是噪声**，别当结论。1.6pct 上 codex 和我们差 0.0011。
2. **逐文件的差异比总分更有信息量**。总分是平均，会互相抵消。
3. **注意数据的信息上限**：有些文件谁都修不回来（如 outputevents 的 charttime、
   demographics 的 anchor_age），这些地方的分差不代表能力差距。
4. **错误级指标和 composite 可能反向**：composite 看的是跟 gold 的对齐，
   错误级指标看的是跟注入日志的对齐。一个 agent 可能总分高但改错得多
   （改了不该改的、或者漏改了但整体对齐还行）。
5. **别用旧口径的数字跟新口径比**（`评测规范.md` §4）。
6. **别把「agent 正确删掉的行」当成漏检**。N18 的 raw 比 gold 多 259 万行，
   agent 删对了；旧口径会把这些行里的注入错误算成 b_missing，Det F1 从 0.997 掉到 0.699。

## 8. 给协调方的 checklist

- [ ] 每个评分方都跑了**校准包**，分数落在期望值容差内
- [ ] 所有评分方的 `recover_clean_key` 一致
- [ ] 所有评分方的 `exclude_rows_not_in_gold` 一致
- [ ] 所有评分方用的是**同一份规范版本**（在规范的版本号/日期处标注）
- [ ] 汇总时逐文件对照，不只看总分
- [ ] 分歧归因写清楚了
- [ ] 汇总表里有每个评分方的名字
