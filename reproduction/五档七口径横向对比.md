## 一、七个口径到底在算什么

### 1.1 每个口径 = 四个正交开关的组合

| 口径 | ① 值比对 | ② key 还原 | ③ 排除 gold 外行 | ④ 正确值判据 |
|---|---|---|---|---|
| **v29** | 数值 | ✅ 开 | ✅ 开 | log |
| **str** | 纯字符串 | ✅ 开 | ✅ 开 | log |
| **oldsw** | 数值 | ❌ 关 | ❌ 关 | log |
| **old**（完全老口径） | 纯字符串 | ❌ 关 | ❌ 关 | log |
| **goldv29** | 数值 | ✅ 开 | ✅ 开 | **gold** |
| **goldstr** | 纯字符串 | ✅ 开 | ✅ 开 | **gold** |
| **goldold** | 纯字符串 | ❌ 关 | ❌ 关 | **gold** |

（`oldsw` 没有 gold 版 ⇒ 4 + 3 = 7 个）

#### ① 值比对：`same_value(a, b)`

- **数值**（默认）：`a == b` → 相同；否则两边都能 `float()` 且 `|fa-fb| < 1e-9` → **也算相同**
  （`'0'` vs `'0.0'`、`'160'` vs `'160.0'`）；**NaN 不算相等**
  （agent 写 `'nan'`、log 记空串 ⇒ 判不等）。
- **纯字符串**：只有**字节完全相同**才算相同。

⇒ 这一条决定「同一个值只是写法不同」算不算修对。

#### ② key 还原（`--no-recover-clean-key` 关掉它）

注入器把 raw 行的 **key 列**改坏时（itemid 别名 / hadm 不匹配），agent 修好后
输出里用的是**原值** ⇒ 评分器按 raw 的**脏 key** 查它的行 ⇒ **查不到**
⇒ 那行的非键格会被整片记成 `b_missing`（**假漏检**）。

- **开**：用 log 里该 key 列的 `clean_value` 还原出**干净 key** 再查一次 ⇒ 把这批格捞回来。
- **关**：直接记 `b_missing`。

⇒ 影响面：ICU5000 / K29 / I48 的 itemid 别名注入 + hadm 不匹配。

#### ③ 排除 gold 外行（`--keep-rows-not-in-gold` 关掉它）

agent 输出里没有这一行、**gold 里也没有** ⇒ 这一行本就不该出现（agent 删对了）
⇒ 默认**排除**（记 `row_not_in_gold`，不计分）。

- **关**：算成 `b_missing`（漏检）。

⇒ **只有 I48 真正受影响**：它的任务含 **cohort 筛选**（agent 要自己推导入选规则），
raw 1,723.9 万行 → reference 1,276.8 万行 ⇒ **agent 该删 383.8 万行（22.3%）**。
ICU5000 / K29 的注入错误**天然只落在 gold 存在的行上** ⇒ 对它们几乎无影响。

#### ④ 正确值判据（`--clean-from-gold` 打开它）

「这一格该修成什么」的判据：

- **log**：用 log 的 `clean_value`（注入器写日志时的**原样字符串**）。
- **gold**：用 **gold(reference) 那一列的真实值**。

为什么要开：各档 log 的 `clean_value` **渲染不同**（`'160'` vs `'160.0'`），
纯字符串口径下 agent 写 `'160.0'`、log 记 `'160'` 会被判成「没修好」
⇒ **罚的正是「与 gold 逐字节相同」的对答案**。

⇒ 只影响纯字符串口径（数值口径下两者数值相等 ⇒ `v29` 与 `goldv29` 几乎一致，
这个「几乎一致」本身就是评分器正确性的自检）。

### 1.2 逐格怎么记账（七个口径共用）

对每一处**注入错误**（`cell_update`）与**注入行**（`duplicate` / `insert`）：

| 记账 | 含义 |
|---|---|
| **b_clean** | agent 写的值 == 正确值（**修对了**） |
| **b_dirty** | agent 写的值 == 注入的脏值（**没动**） |
| **b_wrong** | 改成了别的值（**改错了**） |
| **b_missing** | agent 输出里根本没有这一行（**漏了**） |
| **dup_removed / dup_kept / dup_row_gone / dup_row_short** | 重复行：删对了 / 留着 / 整行没了 / 数量不足（按该 key 在 gold 的行数作基准） |
| **leak_removed / leak_kept** | 插入的标签泄露行：删掉了 / 留着 |
| **fp_det** | 「改对了不该改的格」（误报检测） |
| **natural_noise** | 同一数值、写法不同（只在纯字符串口径出现） |

### 1.3 Det / Rep 的公式

```
tp_det = b_clean + b_wrong + dup_removed + leak_removed
fn_det = b_dirty + b_missing + dup_kept + dup_row_gone + dup_row_short + leak_kept
tp_rep = b_clean + dup_removed + leak_removed
fp_rep = b_wrong + dup_kept + dup_row_gone + dup_row_short + leak_kept

P_det = tp_det / (tp_det + fp_det)      R_det = tp_det / (tp_det + fn_det)
P_rep = tp_rep / (tp_det + fp_det)      R_rep = tp_rep / (tp_rep + fp_rep + fn_det)
F1    = 2PR / (P + R)
```

⇒ **Det 看「有没有发现」**：`b_dirty`（没动）和 `b_missing`（缺行）都算**漏检**。
⇒ **Rep 看「改对没有」**：`b_wrong` 算**误报**；Det 高而 Rep 低 = 「知道错了但恢复不出原值」。

### 1.4 公共前置：索引空间（七个口径都依赖）

`modification_log.csv` 记的行号是**注入前**的行空间，而 raw 里插了 duplicate/insert 行
⇒ 评分器要按 `raw行号 = log行号 + 它前面插入的行数`（bisect）映射。

⚠️ **这个映射不能写死**，用**数据探测**逐文件判定（zero / bisect）：
抽 log 条目（带 `dirty_value`），分别按两种映射投到 raw 行号，
看**哪个映射能让 raw 那一行的值真的等于 dirty_value**。

⇒ **I48 的 reference 是 cohort 筛选后的输出表** ⇒ 行数判据会把它误判成 zero
⇒ 索引平移修正被关掉 ⇒ **分数是垃圾**。实测 I48 判 bisect（210/210 命中）。

## 三、怎么读这张表（三条硬约束）

### ① 跨档比**只能看 gold 判据那两档**（goldv29 / goldstr）

**K29 1.6pct 的 log 被按比例改过**（`fix_k29_log_rawform.py --ratio 0.2629`），
它的 str / old 两个 Rep（0.7572）是**按要求调出来的目标值**；
其余四档 log 一个字节没动 ⇒ **纯字符串口径不能跨档直接比**。

### ② **I48 的 old / oldsw 不能跟别的数据集直接比**（结构性偏差）

I48 的任务含 cohort 筛选 ⇒ agent 该删 383.8 万行 ⇒ `--keep-rows-not-in-gold`
把这些行上的注入格记成假漏检：

| 来源 | 1.6pct | 4.7pct |
|---|---:|---:|
| ① cohort 筛掉的行 | 650,544（20.3%） | 3,070,497（20.3%） |
| ② key 被注入改过的行 | 782,704（24.4%） | 4,052,166（26.7%） |
| **①+② 合计** | **1,433,248（44.6%）** | **7,122,663（47.0%）** |
| ③ 真正该评的 | 1,777,268 | 8,028,651 |

**ICU5000 对照 = 0 格**（它的注入错误天然只落在 gold 存在的行上）⇒ **这是 I48 独有的**。
⇒ I48 的 old（Det 0.7296 / Rep 0.5943）被系统性压低，**不是 agent 的错**。

### ③ `v29` vs `goldv29` 的差异是**正确性自检**，不是噪声

数值口径下 log 判据与 gold 判据**应当几乎一致**；残余差异来自 NaN
（agent 写 `'nan'`、log 记空串 ⇒ 数值感知判不等、字符串相等）：

| 数据集 | v29 Rep | goldv29 Rep | 差 |
|---|---:|---:|---:|
| K29 1.6pct | 0.990200 | 0.989745 | 0.00046（NaN） |
| K29 4.7pct | 0.978995 | 0.978995 | 0 |
| ICU5000 1.6pct | 0.953289 | 0.949830 | 0.00346（NaN） |
| ICU5000 4.7pct | 0.893552 | 0.892673 | 0.00088（NaN） |
| **I48 1.6pct** | 0.907893 | 0.907893 | **0** |

## 四、一句话结论

- **检测能力**（v29 Det）：五档都在 0.94~0.999，**I48 0.9986 与 ICU5000 1.6pct 同档**；
  唯一掉档的是 ICU5000 4.7pct（0.9418，b_dirty 263 万 = 哨兵码没改）。
- **修复能力**（goldstr Rep）：K29 最高（0.988/0.978）⇒ ICU5000（0.947/0.863）
  ⇒ **I48 0.908**（I48 任务更难：要自己推 cohort 规则）。
- **原生层**：ICU5000 1.6pct 99.2% > I48 98.1% > ICU5000 4.7pct 97.5% > K29 1.6pct 95.8%
  > K29 4.7pct 88.5%。
- **I48 的 old 口径不是可比口径**（44.6% 的格是假漏检），要跨档比请用 **goldv29 / goldstr**。
