## log 记载约定统一（2026-11-17）—— 只动 1.6pct，4.7pct 一个字节没碰

| 项 | 内容 |
|---|---|
| **动的是谁** | **只有 K29 mimicraw 1.6pct** 的 `test/train/validation` 三份 `modification_log.csv` |
| **没动的是谁** | **K29 mimicraw 4.7pct 的 log 逐字节未动** —— md5 `6e6ba7338c7b99a9bee0a48e31cf9304`（改前 = 改后）✓ |
| **改什么** | 注入器条目的 `clean_value`：**float repr（`'160.0'`）⇒ 原始串（`'160'`）** |
| **md5 指纹** | 1.6pct `test` `763a1fcb2e195d7eaaca80256661c8f5`（改前 `1p6_test__modification_log.csv.pre_rawform.bak`）<br>`train` `d349da58718d98cc489b1082a70adbaa`／`validation` `56d62edc3dd8b81cb383f4323b422392`<br>4.7pct `test` `6e6ba7338c7b99a9bee0a48e31cf9304`（**改前 = 改后** ✓） |
| **规则** | 只转「确为 float repr 的整数」：`float(s)` 是整数 **且** `str(float(s)) == s`。`'160.0'`→`'160'` ✔；`'160'` 不转；**`'04280'` 不转（保留前导零）** |
| **不动的东西** | `dirty_value`（必须与 raw 里实际写入的串一致）；原生错误条目（873 条 `mimic_native_*`）；**所有键列** |
| **脚本** | `reproduction/fix_k29_log_rawform.py`（`--fix` 才写） |
| **改动量** | test 3,236,991 条（`valuenum` 3,205,425 + `amount` 31,566）；train 100；validation 9,030 |
| **核对** | 逐行对比备份：只 `clean_value` 变、只 valuenum/amount 两列、**原生条目 0 改、键列 0 改**、全部「数值相等」、其它列 0 差异 ✓ |

**为什么必须跳过键列 / 保留前导零**：`diagnoses_icd.csv` 的键列含 `icd_code`，
它有 **1,743 条前导零形式**（`'04280'`）。宽松规则（只要是整数就转）会把它们抹成 `'4280'`，
而评分器用 log 的 `clean_value` **按精确字符串**还原被注入破坏的 key ⇒ 还原失败
⇒ 这 **1,743 行**被记成 `row_not_in_gold` 而**排除出评估集**（评估集从 3,671,318 掉到 3,669,575）。
⇒ 严格规则实测**对 4.7pct 的 log 零改动**（该档 log 已是原始串形式 ⇒ 规则幂等）✓

### 为什么 N18 要单独做一套

N18 = ICD-10 **N18 慢性肾病**，是**最后**一个要加原生错误层的数据集。
但它跟前面四族都不一样，**照抄任何一族的 prompt 都会出错**：

| 维度 | icu5000 / K29 | i48 | **N18** |
|---|---|---|---|
| 任务形态 | 单表清洗 | cohort 型 | **cohort 型** |
| reference | 注入前的干净表 | cohort 筛选后的输出表 | **cohort 筛选后的输出表** |
| log 行号空间 | == reference 行号 | != reference 行号 | **!= reference 行号** |
| 输出文件数 | — | 13 | **18**（7 顶层 + 4 icu + 6 multimodal/ed+notes + 1 edstays 主表） |
| 多模态 | 无 | `ecg/` | **`ed/` + `note/`**（且**不注入**错误） |
| 硬区间 itemid | 照抄 K29 列表 | i48 自己的 20 行 | **按 d_items label 文本匹配 ⇒ 21 行** |

⇒ 三处必须自己重做：**① prompt（基线 v1 里根本没有「原生错误」这一节）**
**② 原生格判定（必须按 5 段 key 定位，不能用 icu5000 那版按行号对齐的）**
**③ 打分脚本的 ds-key / 路径**。

### ⭐⭐ 关键机制：harness **第 2 轮起 prompt 只含 feedback** ⇒ 规则只活一个回合

**这才是「越界类 16 格全灭」的真正机制**，不是错误类型不一致（四族都是 T1+T2 两类，同型）。

- 第 1 轮：prompt = 完整任务书（含 itemid→区间对照表）
- **第 2 轮起**：prompt = `[Validation Harness feedback]` + 一句
  "Continue from the same task and context"（`agent/pi_harness.py:767`）
  ⇒ **原始任务书里的区间表不在回合输入里了**
- ⇒ agent **必须在第 1 轮内**把规则抄进 pipeline 代码，否则**规则永久丢失**
  （除非它自己把它写进了产物文件）。

**实测对照**：

| | i48 mimicraw2 的 agent | N18 v2 的 agent |
|---|---|---|
| 日志里提到「生理不可能」 | **1 次** | **0 次** |
| pipeline 里的区间常量 | ✅ `pipeline.py:41` `"220045": (20.0, 300.0)` 等 20 个 | ❌ **完全没有** |
| 修复池分组键 | ✅ `:248` `groupby("subject_id")` | ❌ `groupby(["stay_id","itemid"])` |
| 越界类修复率 | **98.4%** | **0%**（16 格全灭） |

⇒ **「日志里提到几次」不是有效指标**（i48 几乎没聊这题却抄对了 —— 它直接抄进代码）。
⇒ **结构性洞察**：
- **T1（哨兵码）对 agent 是「可有可无」的** —— 它统计 `valuenum` 频次就自己推出来了
  （N18 的 agent 的 `SENTINEL_VALUENUM` 是**自己算的**，不需要 prompt）；
- **T2（越界类）是「只能靠 prompt」的** —— itemid→区间的映射推不出来。
⇒ **prompt 一旦掉链子，掉的必然是 T2**。这不是巧合。

**⇒ prompt v5 的两处加固**（都在「重新跑一次」之前做掉）：
1. **代码骨架 + 自检清单挪到 prompt 末尾**（靠近「输出与复现要求」）
   —— 第 1 轮写代码时末尾的内容最新鲜；
2. **要求 agent 把规则写进自己的产物**：`train_analysis.json` 的 `error_patterns`
   里要有原生错误那条（写明 itemid→区间对照表 + 哨兵码清单 + 修复规则），
   pipeline 里要有对应的**可执行代码**（不是只写在注释里）。
   —— ⚠️ 理由就是上面那条机制：**规则只留在脑子里 / 只留在本回合上下文里，下回合就没了**；
   **写进文件才留得住**（i48 就是这么做的：`train_analysis.json` 有 `error_patterns`，
   `pipeline.py` 里有区间常量）。

### ⚠️ 本轮踩到的第五个坑：API 配额耗尽会静默掐死跑批

- 报错：`RateLimitError/status=429` + `已达到 Token Plan 用量上限`（**是配额，不是速率**）

- ⚠️ N18 这类跑批**很烧配额**：agent 上下文涨到 **50 万 token**（46 万触发压缩），

### ⭐⭐⭐ 第六个坑：**修复时机早于 cohort 筛选 ⇒ 池子被非 cohort stay 污染**

**现象**（4.7pct v2 第 1 轮）：`b_dirty = 0`（31 格**全部**被检出并修了！）
但 **14 格修成了错值**（b_wrong）⇒ **不是漏检，是修错**。

**定位过程**（两个新脚本，把「agent 的值跟哪个口径的中位数一致」逐格比对）：
- `reproduction/n18_native_pool_diagnose.py` —— 7 个候选口径逐个试
  （A=源reference的(subject,itemid)池 ← 真值 / B=(stay_id,itemid) / C=agent的(subject,itemid)
  / D=C且只取区间内 / E=全局同itemid / F=A但剔掉agent没产出的行 / G=A但没排除坏格自己）
- `reproduction/n18_pool_order_check.py` —— 按「该患者有没有非 cohort 的 stay」分组

**结论**：

| 口径 | 格数 |
|---|---:|
| agent 值 == **H**（**全部** stay 的池中位数 = cohort 筛选**之前**算的） | **15** |
| agent 值 == **A**（**cohort 内** stay 的池中位数 = 真值） | 10 |

而 31 格里「该患者**有非 cohort 的 stay**」的正好是 **14 格**，
「只有 cohort stay」的 17 格 —— **精确对应**：
有多余 stay 的患者 → 池子被污染 → 中位数偏 → 修错值。

**根因（agent 自己的代码）**：
```
src/pipeline.py:208   ce = repair_native_errors(ce)          ← 先修原生错误
src/pipeline.py:259   ce = ce[ce["stay_id"].isin(cohort_stays)]  ← 后做 cohort 筛选
```
⇒ 池子 = 该患者**所有 stay** 的读数（含不在 cohort 里的）⇒ 中位数偏。

⚠️ **池子里的其他候选口径全部排除**（F=0 排除「少产行污染池子」、G=0 排除「没排除坏格自己」、
C=D=0 排除「池子口径写错」）⇒ **唯一的原因就是顺序**。

⇒ **prompt 措辞有歧义**：「中位数要在 pipeline 的**最后一步**算」被理解成
「修完注入错误之后」，而不是「**cohort 筛选 + 去重之后**」。

⇒ **prompt v6** 把顺序**写死**：
```
1. 加载 raw → 2. 修注入错误 → 3. 去重 → 4. ⭐cohort 筛选
5. ⭐⭐在这一步之后，才算 (subject_id, itemid) 的中位数池、修原生错误 → 6. 产出 18 个 csv
```
并附「❌cohort 前算 ⇒ 31 格里 15 格修错 / ✅cohort 后算 ⇒ 真值口径」的对照表。

⇒ **这条对所有 cohort 型任务通用**（i48 也是 cohort 型！）⇒ **i48 的 prompt 也该补这条**。

### ⭐⭐ 顺序错误的「显形程度」由**分母**决定 ⇒ 跨档比修复率会被带偏

同一个 prompt（v5）、同一套算法，**顺序对错由 agent 自己排**（1.6pct 那轮排对了，
4.7pct 那轮排错了）。而这个错误**只在「该患者有多余 stay」的格上显形**：

| | validation 31 格里「有多余 stay」的 | agent 的池子口径 | 原生格修复率 |
|---|---:|---|---:|
| 1.6pct | **6 格** | H（cohort 前算）但只有 6 格受影响 | 30/31 = 96.8% |
| 4.7pct | **14 格** | H（cohort 前算） | 17/31 = 54.8% |

⇒ **1.6pct 的 96.8% 里有运气成分**（它只有 6 格受影响）。
⇒ **跨档比原生层修复率之前，必须先看两档的「顺序敏感格占比」。**

**⭐ 但 1.6pct 的 test 数字是干净的**（`reproduction/n18_order_sensitive_subset.py`）：

| test 715 格 | 格数 | 修对 |
|---|---:|---:|
| **顺序敏感格**（患者有多余 stay） | 237（33.1%） | **236（99.6%）** |
| 顺序无关格 | 478（66.9%） | 475（99.4%） |
| 全部 | 715 | **711（99.4%）** |

⇒ 那 237 格**几乎全对** ⇒ **1.6pct 那轮 agent 在 test 上确实做了「cohort 筛选之后」再算池子**
（顺序对了）⇒ **test 的 99.4% 是真能力，不是运气**。
⇒ 而 4.7pct 那轮在 validation 上顺序错了 ⇒ 它的原生层分数会被系统性压低。

⇒ **结论**：v5 的 prompt **不足以保证顺序**（agent 自己排，排在哪儿全凭它）⇒
**v6 把 6 步顺序显式写死是必需的**（已做）；而 1.6pct 已有的结果（val 0.925112 /
test 0.918532 / 原生层 711-715 = 99.4%）**仍然有效、且经得起这个口径的检验**。

### ⚠️ 本轮踩到的**第八个坑**：独立重放这一关判 0 —— `replay.argv` 的契约要写死

**现象**（N18 1.6pct v7 run，2026-11-24）：第 1 轮 val 打分 **0.878045（promoted）**，
结果在**独立重放**这关挂掉：

```
[Harness] independent replay: status=EXECUTION_FAILED score=0.000000
[Harness] replay repair 1: Agent turn started
[Harness] replay repair 1: status=INVALID_SUBMISSION score=0.000000
[Harness] replay repair 2: Agent turn started
```

⇒ agent 为此烧了两轮去**猜** harness 的执行契约（cwd 是不是 workdir？
`/usr/bin/env` 在不在？相对路径行不行？shebang 行不行？shell launcher 行不行？），
并且它第一次的修法（把 `argv[0]` 改成**绝对路径**的 shell launcher）被校验器直接拒：
`submission replay.argv cannot contain static absolute paths`。

**契约其实是可以写死的**（源码 `agent/pi_harness.py` + `agent/pi_harness_sandbox.py`）：

| harness 实际做的事 | 源码位置 |
|---|---|
| `cwd=str(replay_workdir)` —— 重放的 cwd **就是** workdir（相对路径能解析） | pi_harness.py:896 |
| `argv[0] in {"python","python3"} ⇒ argv[0] = sys.executable` | pi_harness.py:883 |
| `command = ["/usr/bin/sandbox-exec", "-f", profile, *argv]` | pi_harness.py:885 |
| sandbox **只放行 harness 自己那个 python 可执行**（`allow process-exec (literal …)`） | pi_harness_sandbox.py |
| sandbox 可读：workdir / `{raw_root}` / `{train_reference}`；可写：workdir / HOME / TMPDIR；**无网络** | 同上 |
| `{workdir}` `{output_dir}` `{raw_root}` `{train_reference}` 替换成**绝对路径** | pi_harness.py:190-209 |
| 校验器：`argv[0]` 不能是 shell（sh/bash/zsh/env…）；必须含 `{raw_root}` 与 `{output_dir}`；**任何不含占位符的项不得是绝对路径** | pi_harness.py:154-172 |

⇒ **两条致命细节**（agent 猜的正是这两条）：
1. **`argv[0]` 必须是 `"python3"` / `"python"`**（harness 会换成它自己那个 python，
   **脚本作为参数传入 ⇒ 不解析 shebang**）。
   ⚠️ **把脚本本身当 `argv[0]`**（`"run_pipeline.py"` / `"{workdir}/run_pipeline.py"`）
   ⇒ 会**按 shebang 启动**，而重放环境的 PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`
   ⇒ `#!/usr/bin/env python3` 解析到 **`/usr/bin/python3`（macOS 的 Xcode CLT 壳程序）**
   ⇒ 它在 sandbox 里读不到真正的解释器 ⇒ 启动失败 ⇒
   harness 报 `sandbox-exec: execvp() of 'run_pipeline.py' failed: No such file or directory`
   （**ENOENT，看着像文件不存在，其实是解释器起不来**）⇒ 整轮 0 分。
   ⇒ **解释器交给 harness 指定，脚本由你当参数传。**
2. **「静态绝对路径」被校验器直接拒** ⇒ 脚本路径要么相对、要么写成 `{workdir}/xxx.py`。

**证据链**（都在盘上，可复核）：
- harness 自己写的失败档案 `host/replay/failure_0001.json`：

- 两次 SUCCESS 的 run 的 `argv[0]` 都是 `"python3"`（harness 换成 `sys.executable`）⇒ 不走 PATH 查找 ⇒ 不踩 CLT 壳。

⇒ **正确的写法有两条，都是本仓已经跑通过的**（取自两次 SUCCESS 的 run 的 `submission.json`）：


**现象**（4.7pct `_v1`）：第 4 轮起连续 4 次

```

```

⇒ 4 次重试全是同类错 ⇒ worker 崩 ⇒ **那一遍 run 零产出**（好在该 run 的第 1 轮已 promoted，
兜底收尾还能救回 0.927668；否则连这个都没有）。

**机制（查清了，之前归因错了）**：
**不是「最终汇报的结构」，是「上下文压缩时交的续跑摘要」。**

| 环节 | 实测 |
|---|---|
| 上下文上限 | `M3_CONTEXT_SIZE = 512_000` |
| 压缩触发线 | `trigger = 512,000 − 16,384 = **495,616**`（实测 4 次激活都在 **496,534 / 497,303 / 498,072 / 498,840**；AgentScope 自己的内部阈值是 460,748，但实际触发的是 harness 这条） |
| 压缩时要交的摘要 | `PiCompressionSummary`（`agent/pi_runtime.py:92`）—— **10 个字段，全部是 `str`，全部必填** |
| 怎么进 schema 的 | `create_pi_context_config()` 把 `PiCompressionSummary.model_json_schema()` 传给 AgentScope 的 compressor |

⇒ 模型把某个字段写成**数组/对象**（把「3 条发现」写成 `["a","b","c"]`）⇒ `is not of type 'string'`；
**漏一个字段** ⇒ `is a required property` ⇒ 本轮失败 ⇒ 重试；**连挂 4 次 ⇒ worker 崩**。

**实测失败率**（从三个 run 的日志里数 `[Compression Start]` / `[Compression End]`）：

属个案，不是通用失效模式）。

**② prompt 里把 `replay.argv` 契约写死 ⇒ 重放这一关才跑得通**
N18 上同一族的 prompt 没写契约时，重放直接 `EXECUTION_FAILED`（整轮 0 分）；
校正类这条 prompt 写了 ⇒ **重放 rc=0**（stderr：`repaired 21 cells -> .../results/hospital.csv`）。
⇒ 契约四条：`argv[0]` 必须是 `"python3"` / 脚本路径相对或 `{workdir}/…` /
不许静态绝对路径 / 必须含 `{raw_root}`+`{output_dir}`。

**③ 模板里有一处事实错误**（只有 hospital 有）：它写 train 对照样例是
「同一个表的**前 10 行切片**」，而实际切分是
`selection = curated_greedy_changed_column_coverage_v1` ⇒ **按 index 散布挑出来的 10 行**
（实测 train 的 index = 158/214/229/239/257/265/333/387/533/699，整表前几行是 1/2/3/…）。
另外三个模板写的本来就是「从整张表里挑出来的 N 行，不是前 N 行」⇒ 已统一
（`reproduction/make_correction_prompt.py` 里的 ① 步）。

**④ agent 的最终回复过长会**打爆 harness 的 JSONL 控制通道** ⇒ 被误判成 crash**
rayyan val 收尾报 `worker_crash_finalized`，但分数完全有效（`SUCCESS_REPRODUCIBLE`、0.983182 逐位可复现）。
根因是**传输层**不是 agent：worker 客户端没给 `create_subprocess_exec()` 传 `limit=`，
asyncio 默认行上限 64 KiB；agent 某轮回复超限 ⇒ `readline()` 抛 ValueError 且**丢弃已读字节**
⇒ 通道永久错位 ⇒ 之后每轮都读到上一轮的残留 ⇒ `polluted the JSONL control channel`
⇒ `Pi worker response id mismatch` ⇒ 重试把整轮重跑 4 次 ⇒ 兜底收尾记成 crash。
**完整机理 + 补丁见下面 rayyan 小节。**

**⑤ `{train_reference}` 注入的是「目录」不是「csv 文件」⇒ agent 的脚本常直接 `open()` 就炸**
harness 的公开契约（`agent/pi_harness.py` `_initial_prompt`）写的是
`Train reference: …/train/reference`（**目录**），replay 的 `{train_reference}` 占位符
替换的也是 `str(train_reference.resolve())`（**同一个目录**）；
harness 自己内部用 `_first_regular_file()` 取文件，**但给 agent 的是目录**。
⇒ 四档 prompt 的 replay 契约那段措辞**完全相同**，**没有一句提示这一点**
⇒ agent 写 `open(train_reference)` 就 `IsADirectoryError` ⇒ **重放 EXECUTION_FAILED（0 分）**。

实测：
- **hospital**：同样踩到（那次的修复回合里 agent 写了 `resolve_reference()` 吃 5 种形态，
  目录形态是其中一种）；
- **tax**：`host/replay/failure_0001.json` ⇒
  `IsADirectoryError: [Errno 21] Is a directory: '…/tax_curated10_val20_v1/train/reference'`
  （`clean.py` 的 `read_table()` 第 653 行）；
- **rayyan / beers**：没踩到（agent 恰好把目录当目录处理了）⇒ **4 档里 2 档踩到**。

⇒ **val 的「独立重放」这道保险真的救了场**：tax 的 val 交付表 **score=1.000000（满分）**，
但重放 0 分 ⇒ harness 自动进「replay repair」回合让 agent 修 pipeline
（`[Harness] replay repair 1: Agent turn started`）⇒ **不是直接交一个"分数好看但跑不起来"的产物**。
⇒ **后续跑批的 prompt 建议加一句**（本次 tax 在跑，**不动它的 prompt**）：
「`{train_reference}` 注入的是**目录** `train/reference/`（里面才是 `<name>.csv`），
脚本要先判断是目录还是文件，是目录就取其中唯一的 `.csv`」。

#### 坑四：agent 最终回复过长 → JSONL 控制通道读爆 → **传输层**错位 → `worker_crash_finalized`

rayyan val 报的 `stop_reason=worker_crash_finalized`，但**分数是有效的**
（`status=SUCCESS_REPRODUCIBLE`、`reproducible_score == best_score == 0.983182`）。
查下来**不是 agent 的锅，是传输层的锅**（日志
`correction_agent_run/logs/rayyan_correction_val_seed666_v1.log` 第 15152 / 15153 / 16357 / 17041 行）：

1. `agent/pi_worker_client.py` 的 `create_subprocess_exec()` **没传 `limit=`**
   ⇒ asyncio 默认行上限 **64 KiB**；
2. agent 某一轮的最终回复文本超过 64 KiB ⇒ `StreamReader.readline()` 抛
   `ValueError: Separator is not found, and chunk exceed the limit`，
   而且**已读字节被丢弃** ⇒ 控制通道从这一行开始**永久错位**；
3. 之后每次 `run_turn` 读到的都是**上一轮**的残留：
   先读到上一条回复的尾巴 ⇒ `Pi worker polluted the JSONL control channel`；
   再读到上一条请求的正常响应 ⇒ **`Pi worker response id mismatch`**（响应序号落后 1）；
4. driver 的重试包装器（`MAX_TURN_RETRIES=4`）把**整轮重跑**（于是 agent 多跑了 "Round 2 / Round 3"），
   4 次用尽后抛异常 ⇒ harness 走兜底收尾 ⇒ `stop_reason=worker_crash_finalized`；
5. 讽刺的是 **worker 当时回的正是 "Round 3 complete … verified and unchanged in score (0.983182)"**
   —— agent **早就跑完并交付了**，是收尾读响应时才崩。

⇒ 已加补丁（**worktree 本地**）：`eval_handoff/scripts/run_val_harness_ft.py` 里给
`JsonlWorkerClient.start` 包一层，把 worker 的 stdout 行上限放大到 64 MiB，
**不动任何评测/打分逻辑**；主仓共享文件 `agent/pi_worker_client.py` **未改**（其他并行 job 在用）。
⇒ 附带效果：这一族以后的跑批**不会再因为回复过长被误判成 crash**。
⇒ **补丁已实测验证**（`reproduction/verify_worker_stream_limit.py`：起一个假 worker 吐 **200 KB** 的
JSONL 单行）：
   · 打补丁 → 读到 200,000 字符，且**后续两轮 id 不错位** ⇒ PASS；
   · `NO_PATCH=1` → 原样复现 `ValueError: Separator is not found, and chunk exceed the limit`
     （`agent/pi_worker_client.py:272` 的 `readline()`）⇒ 诊断坐实。

### ⭐ 基线是**旧数据集版本**的产出 ⇒ 入包时做了两处「不改值」的变换
`对比结果/` 那批基线跑在 2026-09 的旧切分上：

| 数据集 | 基线产出 | 当前 test gold | 变换 |
|---|---:|---:|---|
| hospital | 1,000 行（含当时 train+val 30 行） | 970 行 | 按 key `index` 取 test 行子集 |
| beers | 2,410 行 | 2,380 行 | 按 key `index` 取 test 行子集 |
| rayyan | 1,000 行 | 970 行 | 按 key `id` 取 test 行子集 |
| tax | 200,000 行，**没有 `__row_id` 列** | 199,950 行 | 按原表行号补回 `__row_id`（= 原行号 0..199999，基线保持原行序）再取 test 子集 |

**只做「补 key 列 + 取 test 行子集」，一个单元格值都没改**；校验器里对基线不是 md5 比对，而是
**重新推导一遍变换再逐行比对**（`verify_ceshi1_package.py` 的校正类段）⇒ 4/4 逐行一致。

### 打分（harness 自己的打分器，在**包内拷贝**上重打；gold = `correction/reference_private`）

| 数据集 | 基线 | 我们 | 差 | 胜者 | 我们的 val | test−val |
|---|---:|---:|---:|---|---:|---:|
| hospital | 0.994722 | **0.997031** | +0.002309 | 我们 | 0.984000 | +0.013031 |
| beers | 0.980497 | **1.000000** | +0.019503 | 我们 | 1.000000 | 0.000000 |
| rayyan | 0.879803 | **0.973187** | +0.093384 | 我们 | 0.983182 | −0.009995 |
| tax | **0.999273** | 0.973634 | **−0.025639** | **基线** | 1.000000 | **−0.026366** |

⇒ **我们 agent 的重打分与 harness 的 score_report 逐位一致**
（hospital 0.997031 / beers 1.000000 / rayyan 0.973187 / tax 0.973634）⇒ 打分链路可复现、包内拷贝无损。

### ⭐ 两条结论（这一族第一次做出 agent↔基线的同口径对比）
**① tax 是基线赢的一档（−2.6 个点）** —— tax 的 test 段 199,950 行 / 121,108 个坏 cell，
规模比前三档大两个数量级；我们的 agent 在 **val 的 20 行上满分**，全表上却**过度泛化**：
把为 20 行归纳的规则套到 20 万行 ⇒ **改坏 0.62% 的干净 cell**（val 看不出来，因为 val 只有 20 行）；
基线规则更保守、几乎没误改（cell 0.9999 / exact 0.9978）。
⇒ **与台账㉗ 的结论一致并补上了量化**：val 分数对大表**没有预测力**，必须看 test。

**② rayyan 是我们赢最多的一档（+9.3 个点）** —— `author_list` 这类**列表列**的 gold 写法不唯一，
基线无差别规范化 ⇒ 大量改错（exact 0.6485）；我们的 agent 在 train 阶段就发现写法不唯一、保留原值
⇒ exact 0.9206。
⇒ **两类失效互补**：我们强在「识别歧义、不乱改」，弱在「规则套太宽、改坏干净 cell」；
基线正好相反（保守 ⇒ 不误改，但不敢修 ⇒ 漏改多）。
