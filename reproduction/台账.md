## log 记载约定统一（2026-11-17）—— 只动 1.6pct，4.7pct 一个字节没碰

| 项 | 内容 |
|---|---|
| **动的是谁** | **只有 K29 mimicraw 1.6pct** 的 `test/train/validation` 三份 `modification_log.csv` |
| **没动的是谁** | **K29 mimicraw 4.7pct 的 log 逐字节未动** —— md5 `6e6ba7338c7b99a9bee0a48e31cf9304`（改前 = 改后）✓ |
| **改什么** | 注入器条目的 `clean_value`：**float repr（`'160.0'`）⇒ 原始串（`'160'`）** |
| **md5 指纹** | 1.6pct `test` `763a1fcb2e195d7eaaca80256661c8f5`（改前 `1p6_test__modification_log.csv.pre_rawform.bak`）<br>`train` `d349da58718d98cc489b1082a70adbaa`／`validation` `56d62edc3dd8b81cb383f4323b422392`<br>4.7pct `test` `6e6ba7338c7b99a9bee0a48e31cf9304`（**改前 = 改后** ✓） |
| **规则** | 只转「确为 float repr 的整数」：`float(s)` 是整数 **且** `str(float(s)) == s`。`'160.0'`→`'160'` ✔；`'160'` 不转；**`'04280'` 不转（保留前导零）** |
| **不动的东西** | `dirty_value`（必须与 raw 里实际写入的串一致）；原生错误条目（873 条 `mimic_native_*`）；**所有键列** |
| **脚本** | `reproduction/fix_k29_log_rawform.py`（`--fix` 才写） |
| **改动量** | test 3,236,991 条（`valuenum` 3,205,425 + `amount` 31,566）；train 100；validation 9,030 |
| **核对** | 逐行对比备份：只 `clean_value` 变、只 valuenum/amount 两列、**原生条目 0 改、键列 0 改**、全部「数值相等」、其它列 0 差异 ✓ |

**为什么必须跳过键列 / 保留前导零**：`diagnoses_icd.csv` 的键列含 `icd_code`，
它有 **1,743 条前导零形式**（`'04280'`）。宽松规则（只要是整数就转）会把它们抹成 `'4280'`，
而评分器用 log 的 `clean_value` **按精确字符串**还原被注入破坏的 key ⇒ 还原失败
⇒ 这 **1,743 行**被记成 `row_not_in_gold` 而**排除出评估集**（评估集从 3,671,318 掉到 3,669,575）。
⇒ 严格规则实测**对 4.7pct 的 log 零改动**（该档 log 已是原始串形式 ⇒ 规则幂等）✓

### ⛔ 与 K29 ㉓ 的四处 icu5000 特有差异（**照抄 K29 会错**）

1. **raw 的行索引空间是混合的**：chartevents 带插入偏移（raw 多 1,740,790 行），
   inputevents / outputevents 是零偏移 ⇒ 构建器与校验器都必须**逐文件自动判定**。
2. **itemid 列上多了一层别名注入**：test 里 **1,632,972 条** `chart_itemid_alias_split`
   （+ 574,828 条 medication 版，合计 2,207,800 条），raw 的 itemid 被改成 `992{2|3}XXXX`
   （实测 **100%** 符合「`992` + (2 或 3) + 原 itemid 末 4 位」）。
   这是 **key 列**错误 ⇒ prompt 里新增一节讲还原规则，并强调「先修 key 列 → 再修 valuenum → 最后去重」。
3. **两层错误叠加的那一层在 itemid 上**：141 格（4.7pct 417 格）「itemid 被改 + 原生错误」
   形态同构、不可判定 ⇒ 排除在 native 层之外。**构建器的自检把这个 bug 抓了出来**
   （原先 reference 改了但 log 没登记，agent 修对了反而被判错）。
4. ⭐ **`value` 文本列只有约三成可用**（K29 是 99.6%）—— icu5000 的 chartevents 里有大量
   **文本型 chart 行**（氧疗方式、约束等级、活动能力…），`value` 列记的是描述性文本
   （`Normal` / `Medium` / `3 rails up`），不是数值。实测 `unit_scale_error` 抽样 2 万格：
   `value == clean_value` 只有 **29.2%**，`value` 非数值 **70.7%**。
   ⇒ K29 prompt 里那句「修注入错误直接抄 `value` 比 ÷100 可靠」**在 icu5000 上不成立**，已改。
   ⇒ 但**判据本身仍成立**：验证器确认 2,450 个原生格 `value` 文本列 **100% == `valuenum`**。

### ⚠️ icu5000 的 ECG 缺口（源数据集自带，**不是** mimicraw 引入的）

`raw` 的 ECG 在 `ecg/record_list.csv` + `ecg/machine_measurements.csv`，
`reference` 的在 `multimodal/ecg_manifest.csv` + `multimodal/ecg_measurements.csv`
（**表名不同、不是同一张表**）。两边 study 集合的差：

| split | reference study | raw study | 缺失 | 缺失占比 | 涉及病人数 |
|---|---:|---:|---:|---:|---:|
| train | 5 | 55 | **3** | **60.0%** | 1（该病人在 raw 里一次 ECG 都没有） |
| validation | 11 | 87 | **0** | 0.0% | — |
| test | 5,458 | 30,048 | **4** | **0.1%** | 3（同样整个病人在 raw 里没有） |

- **根因**：`reference` 的 ECG 是**按 stay_id 关联**出来的（每行都带 stay_id / hadm_id）；
  `raw` 的 ECG 是**按 subject_id 抽**的（`record_list.csv` 里根本没有 stay_id / hadm_id 列）。
  两个口径对少数病人不一致 ⇒ **gold 比 raw 多行**。
- **不是** MIMIC 原生错误、**不是**注入错误、**不是** mimicraw 引入的
  （mimicraw 只改 `icu/chartevents.csv`，两档 ECG 表逐字节相同）。
- **影响**：test 只缺 4 行 / 5,458 行 = **0.1%** ⇒ 对最终 composite 几乎无影响；
  但 **train 缺 60%** ⇒ agent 在 train 对照里会看到「reference 有 3 行 raw 没有」，
  自检过不了，可能白白消耗回合（harness 日志里确实看到 agent 在自己推理 ECG 的 join 规则）。
- **决策：不修**（保持与源数据集一致；修它会让正在跑的 val 实验前后不一致）。
  代价可量化（train 60% / test 0.1%），且 validation 上缺口为 0 ⇒ agent 有机会自己学会
  「reference ⊆ raw」，不会去编造不存在的行。
- 若将来要修：把 reference 里那几行**补进 raw**（ECG 是干净数据，本就该原样出现在 raw 里），
  使 `reference ⊆ raw` 严格成立。工具：本次的检查逻辑见下。
