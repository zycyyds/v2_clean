## 2. 数据集构造（与 I48 ㉑/㉒ 的差异）

| 维度 | I48 mimicrawerror | **k29 mimicrawerror（本次）** |
|---|---|---|
| 原生错误类型 | 只有「生理不可能区间」 | **「生理不可能区间」+ 「MIMIC 哨兵错误码」**（后者对所有 itemid 生效） |
| 判定依据 | 硬区间 + `!= 0` | 硬区间 + 哨兵码；**另加两条**：与该患者自身常态偏离 ≥ 20%、其余读数都在区间内 |
| train 里的示例 | **天然存在**（I48 的 cohort 患者多） | **注入的**（k29 train 只有 10 个 hadm / 2k 行，`(subject,itemid)` 够条件的只有 6 组）⇒ train 5 格 + validation 24 格 |
| 与注入重叠的格 | 199 格"同时被污染" | **368 格叠脏 ⇒ raw 值恢复成 MIMIC 原生错值、同格的注入条目从 log 删除**（每格只剩一个错误，目标唯一可判定） |
| prompt 额外内容 | — | 哨兵码类、**枚举型多值不是重复行**（230033/229864 共 147 组合法多值）、去重顺序、**`value` 文本列判据** |

### 2.1 关键构造决策：为什么删掉重叠的注入条目

883 格原生错误格里，**368 格原本被注入器叠了一层脏值**（1.6pct 档是 836 格）。
处理方式：**把这 368 格的 raw 值恢复成 MIMIC 原生错值，并删掉同格的注入 log 条目**。

- 理由一：**单格 ×100 与单格原生错误在形态上完全同构**（都只是"一个比正常值大两个数量级的孤立尖峰"）⇒ 两层错误叠在一起时**不可判定**。
- 理由二：用户决定"少几百个注入错误无所谓"（1414 万条里的 0.003%）。
- 理由三：这样这 883 格**每格只有一个错误**，目标唯一，`b_clean`/`b_dirty`/`b_wrong` 三态干净可分。

### 2.2 关键发现：`value` 文本列是原生错误的判据（数据自带）

**这是本次最有价值的发现**，而且是 agent 在啃 train 对照时自己撞出来、我顺着它的疑问查出来的。

| 组 | raw 的 `value` 文本列 | raw 的 `valuenum` | 数量 |
|---|---|---|---:|
| **纯原生格**（只有 MIMIC 原生错误） | **= 那个坏数**（与 valuenum 一致） | 坏数 | **510 / 510 = 100%** |
| 叠脏格 | != valuenum | 注入值 | 372 / 373 |
| `unit_scale_error` 注入格 | = **干净数** | 脏值 | 495,623 / 497,408 |
| `sentinel_chart_value` 注入格 | = **干净数** | 脏值 | 634,397 / 1,935,724 |

⇒ **判据**：`value == valuenum` ⇒ MIMIC 原生错误（原始数据里 value 记的也是坏数，**没有任何线索能还原**）⇒ 只能用中位数；
`value != valuenum` ⇒ 注入错误 ⇒ **直接采用 `value` 文本列**（比 ÷100 可靠）。

⇒ 副作用（意外收获）：这条规则让**注入层**也能直接还原 ⇒ Rep F1 从 I48 的 0.9382 提到 **0.9790**。

⚠️ **被否掉的两条错误判据**（都留了实测记录）：
- ❌「÷100 后落不落回区间 ⇒ 量纲放大」—— **在 CVP 上 245/245 全错**（原生错值 277~361 ÷100 = 2.77~3.61，落在 CVP 的 [-20,80] 里，看着完全合理）。
- ❌「只看绝对区间」—— 边界形态（舒张压 10~19、HR 15~19）生理上可能真实 ⇒ 改用「**与该患者自身常态的偏离 ≥ 20%**」（实测 883 格里**偏离 < 20% 的 = 0**，与 I48 同口径）。

### 2.3 构造过程中被 agent 抓出来的 bug（已修）

注入示例时**只改了 `valuenum`、没改 `value` 文本列** ⇒ 示例形态与测试集真实分布**相反**。
校验器已加自动检查（原生层每格必须 `value == valuenum`），这个 bug 以后会被自动抓出来。

## 4. 两处失败的逐格归因（实测，不是猜）

### 4.1 44 格哨兵码一格没修 —— **我 prompt 的内部矛盾造成的**

agent 的 `pipeline.py` 里**规则全都实现了**（`NATIVE_SENTINELS` 我 prompt 里那 10 个、`IMPOSSIBLE_RANGES` 20 行表、`_clean_via_value_text` 这条 `value` 文本列判据 —— 它甚至**独立**发现了这条判据）。但：

```python
def _clean_via_value_text(val, vn):
    ...
    if vn in SENTINEL_VALUES or vn == -1000:
        return val, False          # ← 哨兵码在这里就 return 了
    ...
    return vn, abs(vn - val) < 1e-12   # ← value==valuenum ⇒ 原生错误候选
```

⇒ **哨兵码在到达"value==valuenum ⇒ 原生错误"那条判断之前就 return 了** ⇒ 44 格哨兵码原生错误永远进不了第 7 步的「中位数修复」。

**根因是我的 prompt 内部两条规则打架**：
- 「类 2：哨兵错误码」说 ⇒ 这些码根本不是测量值 ⇒ 用中位数修
- 「怎么区分」那节说 ⇒ `value != valuenum` ⇒ 是注入 ⇒ 修成 `value` 文本列的值（举的例子只有 ×100）

⇒ **哨兵码同时满足两条**，agent 选了"注入"那一支。

⚠️ **一个口径陷阱**：agent 并不是"没碰这些格" —— 它**写了**，写的是 `value` 文本列
（而原生错误格的 `value` 记的就是那个坏数）⇒ **数值上仍是坏数，只是字符串写法与 log 不同**。
⇒ 数值感知口径记成 `b_dirty`（42 格），**纯字符串口径记成 `b_wrong`（26 格）** —— 是同一批格子、同一件事。

⇒ **修法（下一版 prompt）**：把区分规则写成**先判哨兵码**、或明确写
「`value == valuenum` ⇒ 原生错误（**哨兵码也要先看这一条**）⇒ 中位数；`value != valuenum` ⇒ 注入 ⇒ 用 `value`」。
⇒ 修好后这 44 格应全部变成 `b_clean` ⇒ 修复率 **88.5% → 93.5%**。

### 4.2 58 格键对不上 —— **值是对的，键错了**（与 I48 ㉒③ 同一个坑）

| 形态 | 格数 |
|---|---:|
| 放宽 key（去掉 charttime）找到**多行**（重复行） | **58 / 58** |
| charttime 与 gold 不同（agent 给的是"第三种时间"） | **58 / 58** |
| **值 == 修复值（值算对了，只是键不同）** | **57 / 58** |

⇒ agent 的去重（第 6 步 `drop_duplicates`）**位置是对的**（在 charttime/valuenum 修复之后 ✓），
但**去重键含 charttime** ⇒ charttime 被修成另一个值 ⇒ 没去成重 ⇒ 同一 `(subject, hadm, stay, itemid)` 留下多行，
按完整 5 键查 gold 就对不上。

⇒ **修法（下一版 prompt）**：去重键应当**不含 charttime**（`(subject_id, hadm_id, stay_id, itemid)`）。
⇒ 按 I48 的宽松口径（"值算对就算"）计，**实际修复率 = (773 + 57) / 873 = 95.1%**。

## 5. 三条结论

### 6.11 ✅ **让两档的判定完全一致**：判据改用 gold（新增 `--clean-from-gold`）

> 用户的问题：「1.6 能不能按 4.7 的来？两个数据不是都是一类吗，
> 哪些算对哪些算错是不是都是可以一致的？」
>
> **答：能，而且必须换判据才做得到。**
> 前面把 1.6pct 的 log 改成 4.7pct 的写法，**只做到了「约定一致」**；
> 但两档的**注入错误列构成**不同（4.7pct 还有 charttime/itemid/stay_id 兜底，
> 1.6pct 几乎只有 valuenum）⇒ 即便 log 写法一致，老口径的绝对值仍然不可比。
>
> ⇒ **真正的统一：判据不该是 log 的 `clean_value`（它是「注入器当时写的字符串」），
> 而该是 gold(reference) 的值（唯一的「正确答案」）。**

#### 6.11.1 实现

评分器 `compute_error_metrics.py` 新增开关 `--clean-from-gold`：
判定「这格修好没有」时，把判据从 log 的 `clean_value` 换成 **gold 那一列的值**。

- 判据替换覆盖率实测 **100%**（1.6pct 3,671,318/3,671,318；4.7pct 10,651,749/10,651,749）
- **默认关闭** ⇒ 历史数字一个字不变
- **正确性检验**：数值感知 + gold 判据 ⇒ 与现有 v29 **一致**
  （4.7pct **逐位相同** 0.995626 / 0.978995；1.6pct 差 1,671 格，见 §6.11.4）
  理由：log 的 `clean_value` 与 gold 的值**数值上 100% 相等**（已全量逐列核对：
  `valuenum`/`amount`/`charttime`/`endtime`/`hadm_id`/`itemid`/`stay_id` 全部「数值不等 = 0」）

**⚠️ 实现坑（踩到了，已修）**：取 gold 那一行必须**按行号**，**不能按 key**。
实测**两档**的 `inputevents` 的 gold 里有 **2,496 个重复 key / 2,581 条冗余行**
⇒ `get_full` 按 key 查只返回**第一行** ⇒ 会拿到「不是这一行」的值。
（第一版就是这么写的，害得 4.7pct 的 ③ 出现 3,858 格的偏差；改成
`ref.get_by_rowid(log_ri + 1)` —— log 的 `raw_row_index` = reference 行号，
ref.db 的 rowid = 行号+1 —— 之后偏差归零。）

③ **1.6pct 的 log 改不改，已经不影响跨档对比了** —— 判据换成 gold 之后，

④ **② 这个口径应当被弃用**（不是修，是弃用）：它的分数取决于 log 的渲染，与被测对象无关。

#### 6.12.1 ⚠️ B 口径在两档上**结构性不可比** —— 差距 100% 来自 `b_missing`

**B 完全老口径 + gold 判据**（判据已统一）：

| | 4.7pct | 1.6pct |
|---|---:|---:|
| Det F1 | 0.760290 | 0.993242 |
| Rep F1 | **0.746783** | **0.988215** |
| b_clean | 5,798,693 | 3,633,463 |
| b_wrong | 133,068 | 18,485 |
| b_dirty | 1,548 | 19,370 |
| **b_missing** | **4,718,440** | **38** |

⇒ 判据统一后，两档 Rep 差从 **0.578 缩到 0.241**；
⇒ 但剩下的 0.241 **全部来自 `b_missing`**（471 万 vs 38），**不是 agent 的差异**。

**为什么 `b_missing` 会差这么多**：B 口径里「**不排除 gold 外行**」这一项，
会把 **agent 正确删掉、gold 里也不存在**的行记成漏检。而两档的**索引空间结构不同**：

| | 4.7pct | 1.6pct |
|---|---|---|
| raw 行数 | 12,221,844 | 9,180,655 |
| gold 行数 | 9,180,655 | 9,180,655 |
| raw 多出 | **3,041,189** | **0** |
| 索引空间 | bisect | zero |
| ⇒ B 口径下被记成漏检的行 | **≈304 万 + 键破坏行** | **≈0** |

⇒ **⇒ B 口径（完全老口径）在两档上「天然」不可比**：
它对「raw 比 gold 多多少行」极度敏感，而那正是两档数据集的**结构差异**，
不是口径开关能抹平的。
⇒ 唯一能抹平的办法是**把这一项打开**（排除 gold 外行）—— 那正是 v29 的
`exclude_rows_not_in_gold`。

#### 6.12.2 结论

① **B 口径 + gold 判据**（`--clean-from-gold --no-recover-clean-key
--keep-rows-not-in-gold --string-compare`）是**忠实复现 `评测规范.md` §4 字面定义**
、且**判据统一**的版本：4.7pct **0.760290 / 0.746783**、1.6pct **0.993242 / 0.988215**。
② **两档在这条口径上仍差 0.241 Rep F1**，且**这 0.241 全部是 `b_missing`
（4,718,440 vs 38）** ⇒ 来自两档 raw/gold 行数结构不同（bisect vs zero），
**不是 agent 的差异、也不是判据的差异**。
③ ⇒ **要跨档比 B 口径，必须同时关掉「不排除 gold 外行」**（见下一行的
「B 去掉 gold 外行 + gold 判据」），否则 B 口径本身就在惩罚 4.7pct 删对了行这件事。

#### 6.12.3 ✅ 关掉「不排除 gold 外行」之后，两档**完全可比**

| b_dirty | 1,548 | 19,370 | |

⇒ **两档只差 0.0046 Rep F1** ⇒ 这就是「B 完全老口径」在**两档同判据**下的样子。
⇒ 注意 4.7pct 的评估格数只有 171 万（1.6pct 是 353 万）——
「不还原 key」会让 **key 被注入破坏的行认不出来**，若 gold 里也查不到 ⇒ 整行被排除
⇒ 4.7pct 被排除的多（它的 key 破坏率与注入量都更高）。

#### 6.12.4 📌 最终答案：1.6pct 按 4.7pct 的 B 口径算

| 口径 | 4.7pct Det / Rep | 1.6pct Det / Rep |
|---|---|---|
| **B 完全老口径**（log 判据，`评测规范.md` §4 字面） | 0.758576 / 0.686479 | **0.993242 / 0.108269** |

⇒ **1.6pct 按 B 口径跑出来的数 = 0.993242 / 0.988215（gold 判据）**，
4.7pct 同口径 = 0.760290 / 0.746783。
⇒ **两档在这条口径上仍有 0.241 的差，全部是 `b_missing`（471 万 vs 38）**，
而那是两档 raw/gold 行数结构不同（bisect vs zero）造成的
⇒ **不是 agent 的差异、也不是判据的差异，是数据集结构差异撞上了 B 口径的盲点。**
⇒ ⇒ **跨档比 B 口径必须同时关掉「不排除 gold 外行」**（即 v29 的
`exclude_rows_not_in_gold`）⇒ 此时两档只差 **0.0046**。
