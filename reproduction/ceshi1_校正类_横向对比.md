## 读表提醒

1. **基线跑在旧版数据集上，入包时做了两处「不改值」的变换**：hospital / beers / rayyan 的基线输出是**整表**（1000 / 2410 / 1000 行，含当时的 train+val 30 行）⇒ 按 key 过滤出 test 行子集；tax 的基线输出 200,000 行且**没有 `__row_id` 列**（`__row_id` 就是原表行号 0..199999，基线保持了原行序）⇒ 按位置补回 key 列再取 test 子集。**只做「补 key 列 + 取 test 行子集」，一个单元格值都没改。**

2. ⭐ **tax 是基线赢的一档（0.999273 vs 0.973634，低 2.6 个点）**：tax 的 test 段是 199,950 行 / 121,108 个坏 cell —— 规模比前三档大两个数量级。我们的 agent 在 **val 的 20 行上是满分**，但全表上**过度泛化**：把为 20 行归纳的规则套到 20 万行，**改坏了 0.62% 的干净 cell**；基线反而因为规则更保守而几乎没误改（cell 0.9999 / exact 0.9978）。

3. **rayyan 是我们赢最多的一档（+9.3 个点）**：rayyan 的破坏模式里 `author_list` 这类**列表列**的写法不唯一，基线把它无差别规范化 ⇒ 大量改错（cell 0.9632 / exact 0.6485）；我们的 agent 在 train 上就发现 gold 写法不唯一、保留了原值 ⇒ exact 0.9206。

4. **hospital / beers 差距小（+0.2 / +2.0 个点）**：两档的破坏规则偏机械（跨列语义推断 / 格式前缀），两个跑者都能推出来。

5. **`gold/` 是「错误完全修复」的干净表**（已实测）：拿注入器自己的逐 cell 差分档案 `host_private/cell_diff.jsonl` 对着 gold 逐格核 —— hospital 455 / beers 4,282 / rayyan 891 / tax 121,108 个坏 cell，**每一格的 gold 值都等于 clean_value、都不等于 dirty_value**，0 个 key 未命中 （脚本：`reproduction/check_correction_gold_clean.py`）。gold 只含 **test 段**的行。

6. **我们的 agent 重打分与 harness 的 score_report 逐位一致**（hospital 0.997031 / beers 1.000000 / rayyan 0.973187 / tax 0.973634）⇒ 打分链路可复现，且包内拷贝无损。
